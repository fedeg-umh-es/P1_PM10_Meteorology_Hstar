# Parallelization equivalence: 8 parallel single-station runs vs. one sequential 8-station run

- Date: 2026-07-26
- Scope: justify that running `code/e2_met_ireland_run.py` as 8 parallel,
  single-station subprocesses (via its own `--station` flag, 4 concurrent,
  merged post-hoc) is scientifically equivalent to a single sequential
  invocation over all 8 stations, with no change to any experimental result.

## Why this matters

A single sequential run over 1,569 total rolling origins was estimated at
~17 hours from the smoke test's measured rate (~38.6 s/origin, one station,
both conditions, SARIMA + XGBoost). Running each station as an independent
process across 4 CPU cores was used instead to fit the session, per the
task's own instruction to keep methodology, periods, horizons, stride, lags,
models, seeds, and baseline unchanged while allowing execution-strategy
(portability/runtime) adjustments. The claim under test is: **does this
change any single computed value, anywhere, relative to a sequential run?**

## Code-level argument (read directly from `code/e2_met_ireland_run.py` and
`code/e2_met_madrid_shared.py`)

1. **No cross-station state.** `main()` loops `for station in stations:`
   and, for each station, does `station_df = df[df[station_col] == station].copy()`
   then calls `run_backtest_for_station(station_df=station_df, station=station, ...)`.
   Every quantity used inside that call — origins, train/test windows,
   feature medians (`fit_train_feature_medians`), the XGBoost models, the
   SARIMA fit — is derived **only** from `station_df` and the config. No
   variable computed for one station is read by another station's code path.
   Running the loop as `[Birr, Dublin, ...]` sequentially or as 8 independent
   single-station processes (each with `stations = [args.station]`, per the
   `--station` CLI flag already built into the script) executes byte-identical
   code on byte-identical inputs either way.
2. **No shared mutable output during training.** Each shard was configured
   with `results_dir` pointing at its own directory
   (`results/_ireland_regen_shards/<station>/`) via a per-shard config copy
   (all fields except `dataset_path`/`results_dir` verified identical to
   `code/e2_met_ireland_config.json` at config-generation time — see the
   assertion in the config-generation step). No two station processes ever
   opened the same file for writing.
3. **`n_jobs: 1`** is set in `xgboost_params` in the base config and was
   copied unchanged into every shard config — each XGBoost fit is
   single-threaded regardless of how many station processes run concurrently
   on the machine. `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`,
   `MKL_NUM_THREADS=1`, `NUMEXPR_NUM_THREADS=1` were additionally exported for
   every shard process, so BLAS/LAPACK calls inside SARIMA's Kalman filter
   (`statsmodels`) do not oversubscribe the 4 physical cores either — this
   only affects wall-clock time, not numerical results (single-threaded BLAS
   is deterministic; it does not change floating-point summation order
   within one process the way multi-threaded reductions can).
4. **Same seeds.** `xgboost_params.random_state: 42` and top-level
   `random_seed: 42` are present, unchanged, in every shard config (verified
   programmatically: all fields other than `dataset_path`/`results_dir` were
   asserted equal to the base `code/e2_met_ireland_config.json` at
   config-generation time).
5. **Same configuration, periods, origins.** `train_start`, `test_start`,
   `test_end`, `horizon_max`, `origin_stride_hours`, `min_train_rows`,
   `lags`, `calendar_features`, `meteo_features`, `sarima_*`, `dm_horizons`,
   `dm_loss` are identical across all 8 shard configs and the base config
   (same assertion). Rolling origins are generated by
   `generate_rolling_origins(df=station_df, ...)`, a pure function of the
   station's own timestamp column and these config values — identical
   whether invoked from a single multi-station loop or a single-station
   process.
6. **Deterministic merge.** `code/merge_ireland_regenerated_shards.py`
   concatenates each shard's `predictions_all_models.csv` /
   `metrics_all_models.csv` and immediately re-sorts by explicit keys
   (`["station", "model", "condition", "origin", "horizon"]` for predictions;
   `["station", "model", "condition", "horizon"]` for metrics), so the final
   row order does not depend on shard completion order or process scheduling.
   `H_star_*` and DM-HLN are recomputed (H*) or concatenated (DM, which is
   already per-station) from this canonically-sorted combined table using
   the exact same `derive_hstar_ireland`/DM logic as the single-run script.

## What was NOT changed

Stations, train/test periods, forecast horizons (1..24), origin stride (24h),
lags, calendar features, meteorological features, XGBoost hyperparameters,
SARIMA order/seasonal order, DM horizons/loss, random seeds, and the
persistence baseline are byte-identical to `code/e2_met_ireland_config.json`
in every shard. Only `dataset_path` and `results_dir` differ per shard (both
path-portability changes, not scientific parameters), and only `--station`
was passed on the command line (an existing, documented CLI flag of the
unmodified script).

## Empirical verification (post-merge)

The code-level argument above establishes *why* no difference should exist.
It is additionally verified empirically after merging, in
`results/e2_met_ireland_pm10_regenerated/merge_validation_report.md`:
row-count accounting per station/condition/model, uniqueness of
`(station, origin, horizon, model, condition)`, `forecast_timestamp > origin`
for every row, equal valid pairs between each model and persistence, absence
of any Madrid-station rows, and SHA-256 hashes of every final merged output.
